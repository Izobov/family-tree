# Telegram Mini App: вход через Telegram

Дата: 2026-08-03

## Задача

Приложение должно открываться как Telegram Mini App. Два требования:

1. Привязать Telegram к уже существующему аккаунту.
2. Регистрироваться прямо из Telegram, минуя страницы `/login` и `/signup`.

## Решение

Telegram отдаёт мини-аппу строку `initData` — идентификатор пользователя, имя,
`auth_date` и подпись HMAC-SHA256, ключ для которой выводится из токена бота.
Сервер проверяет подпись и превращает её в **обычную сессию Supabase**.

Ключевое решение: механизм сессии в приложении остаётся ровно один. Админ-клиент
выпускает одноразовый magic-link-токен и тут же гасит его через `verifyOtp` на
серверном клиенте из хуков — тот кладёт свои обычные куки. `safeGetSession`,
`getClaims`, обновление токена, RLS и `ensureTree` не трогаются и не знают, что
пользователь пришёл из Telegram.

Отвергнутые варианты:

- **Синтетический пароль из `telegram_id` и серверной соли.** Не нужен секретный
  ключ Supabase, но пароль становится общим секретом: утечка соли компрометирует
  сразу все телеграмные аккаунты, а её ротация запирает всех снаружи.
- **Свой JWT.** Обходит Supabase Auth вместе с обновлением токенов, которое
  пришлось бы писать руками. Supabase переходит на асимметричные ключи, и подпись
  своим секретом там теперь тупик.

## Схема данных

```sql
create table telegram_accounts (
  telegram_id bigint primary key,
  user_id     uuid not null unique references auth.users(id) on delete cascade,
  username    text,
  first_name  text,
  last_name   text,
  linked_at   timestamptz not null default now()
);
```

`bigint`, а не `int`: идентификаторы Telegram уже перевалили за 2³¹.

Оба ключа уникальны, и это вся защита от угона, а не украшение. `telegram_id`
первичный — один Telegram ведёт ровно в один аккаунт. `user_id` уникальный — к
одному аккаунту нельзя привязать второй Telegram. Попытка привязать уже
привязанное упирается в ограничение БД, а не в проверку в коде, которую можно
забыть.

RLS включена, политики только на `select` и `delete` своей строки. Пишет
исключительно серверный эндпоинт под админ-ключом.

## Проверка подписи

`src/lib/server/telegram.ts` — единственное место с криптографией.
`verifyInitData(initData, botToken, now)` возвращает данные пользователя или
`null`, без подробностей о том, какая проверка не прошла.

Порядок: разобрать строку, вынуть `hash`, собрать `data_check_string` из
остальных полей в алфавитном порядке через `\n`, посчитать
`HMAC_SHA256(data_check_string, HMAC_SHA256(botToken, "WebAppData"))`, сравнить
через `timingSafeEqual`.

Затем отвергнуть всё старше суток по `auth_date`: подписанная строка не протухает
сама, и без этой проверки однажды перехваченный `initData` работал бы вечно.
Допуск на рассинхрон часов вперёд — 5 минут.

## Маршрут `/telegram`

Страница с тремя экшнами — обычные POST-формы, как везде в проекте. Сервер
рендерит заглушку со спиннером: `initData` существует только в браузере. Клиент
подгружает SDK Telegram, читает `initData`, кладёт в скрытое поле и сразу
отправляет `auto`.

- **`auto`** — `telegram_id` найден в таблице: выдаём сессию и `redirect(303, '/')`.
  Пользователь видит спиннер и оказывается в дереве. Это и есть «минуя login».
  Не найден — возвращаем `{ status: 'unknown' }`, появляется выбор из двух кнопок.
- **`signup`** — создаём пользователя админ-API с синтетическим email
  `tg-<id>@telegram.local`, пишем связку, выдаём сессию. Пароля нет: Telegram уже
  подтвердил, кто это. Дерево создаст `ensureTree` при первом входе в `(app)`,
  как и всем остальным.
- **`link`** — принимает email и пароль. Пароль проверяется на **отдельном
  одноразовом клиенте**, а не на `locals.supabase`. Это держит инвариант «сессия
  выдаётся только после того, как всё остальное удалось»: иначе при провале
  вставки связки пользователь остался бы залогинен, но не привязан.

## Почта аккаунта из онбординга

У телеграмного аккаунта почта синтетическая. Если в онбординге («Расскажите о
себе») указан email, он прописывается и в аккаунт — так аккаунт остаётся
опознаваемым, и есть куда прислать письмо в будущем.

Восстановления пароля не делаем, поэтому **само по себе это в веб не пускает**:
пароля у телеграмного аккаунта нет. Говорим прямо, чтобы не выглядело обещанием.

Поле email необязательное, и это в первую очередь контакт человека в дереве, а
запись в аккаунт — бонус сверху. Поэтому **онбординг из-за него не падает**: если
почта пустая или уже занята другим аккаунтом, человек и дерево создаются как
обычно, аккаунт просто остаётся на синтетической почте. Ронять создание дерева
из-за необязательного поля несоразмерно.

Переписывается только синтетическая почта. Настоящую, введённую при обычной
регистрации, онбординг не трогает.

## SDK Telegram

Нужен ради трёх вещей: `initData`, `ready()` и `expand()`. Без `expand()` на
части клиентов окно открывается в половину экрана, и дерево оказывается в щели.

Грузить его всем подряд не будем — веб- и PWA-пользователям он не нужен и стоит
лишнего запроса к чужому домену. Успешный вход через Telegram ставит куку `tg=1`,
корневой layout видит её и только тогда подгружает SDK.

Нативная кнопка «назад» Telegram и тема из `themeParams` — вне этой работы. Своя
нижняя панель в вебвью работает.

## Что меняется в блоке уведомлений

Задачи 20–24 переписываются отдельно, здесь только направление: внутри Telegram
Web Push не работает — вебвью не даёт ни service worker с push, ни разрешения на
уведомления.

Отпадают VAPID-ключи, таблица `push_subscriptions`, подписка в service worker и
запрос разрешения. Расчёт ближайших событий и `notifications_sent` для
дедупликации остаются. Крон вместо Web Push зовёт Bot API `sendMessage`, адресат —
`telegram_id`. Колонка `user_settings.push_enabled` переименовывается в
`notify_enabled`. Кто Telegram не привязал — уведомлений не получает.

## Тесты

`verifyInitData` — чистая функция, покрывается юнит-тестами полностью: валидная
подпись, подделанный `hash`, `hash` неверной длины, протухший `auth_date`, дата из
будущего, отсутствующий или битый `user`. Тест сам подписывает данные фиктивным
токеном тем же алгоритмом.

Сквозной тест реального Telegram не поднимет и не должен: Playwright запускается с
известным тестовым `TELEGRAM_BOT_TOKEN`, тест конструирует валидный `initData` и
проходит оба пути — регистрацию и привязку к существующему аккаунту. Это покрывает
ровно те два требования, с которых всё началось.

Бота создаёт владелец проекта, URL мини-аппа —
`https://family-tree-seven-eosin.vercel.app/telegram`.

Именно этот домен: `family-tree-ivan-izobovs-projects.vercel.app` закрыт
аутентификацией Vercel и отдаёт 302 на `vercel.com/sso-api`, внутри Telegram
пользователь упёрся бы в чужую форму входа.

`TELEGRAM_BOT_TOKEN` нужен в `.env` и в переменных Vercel для production.
`SUPABASE_SECRET_KEY` в рантайме уже нужен крону, новой зависимости не появляется.
