# Family Tree — дизайн

Дата: 2026-07-30

## 1. Что делаем

Небольшое веб-приложение для построения собственного семейного дерева. Пользователь
регистрируется по email и паролю, строит дерево из членов семьи, правит информацию о
каждом (дата рождения, дата смерти, About, контакты) и получает уведомления о днях
рождения и годовщинах свадеб.

Приложение — PWA: ставится на телефон с домашнего экрана, работает в `standalone`,
без сети показывает последнее загруженное дерево.

Мобильный телефон — основной сценарий использования, десктоп — вторичный.

офлайн-синк с очередью правок, email- и SMS-каналы уведомлений.

## 2. Ключевые решения и их обоснование

### 2.1 Диаграмма: family-chart, не DHTMLX Diagram

Изначально предполагался DHTMLX Diagram. Проверка показала, что бесплатная
GPL-редакция существует (`@dhtmlx/diagram` 6.1.6, GPL-2.0-only, активно
поддерживается), то есть лицензия не была бы блокером — но она потребовала бы
публичного репозитория под GPLv2, поскольку библиотека уезжает в браузер
пользователя, а это распространение.

Решающим оказалось другое. Документация DHTMLX по touch-поддержке заявляет ровно три
жеста: тап, двойной тап (правка текста фигуры) и «зажать и тащить» (перетаскивание
фигуры). **Pinch-to-zoom и панорамы холста одним пальцем в списке нет**, а одним
пальцем по умолчанию перетаскивается узел — то есть при листании дерева на телефоне
пользователь разваливает раскладку. Тач-модель DHTMLX рассчитана на редактор схем на
планшете, а не на навигацию по дереву со смартфона.

`family-chart` подходит по двум причинам:

1. Зум и панорама через d3-zoom, у которого pinch и тач-панорама нативные.
2. Модель навигации «один человек в фокусе, родители сверху, супруги сбоку, дети
   снизу, тап по родственнику перецентрирует» — это правильная мобильная
   архитектура. Дерево на 30 человек на экране 390px физически нечитаемо целиком:
   либо два узла крупно, либо всё дерево в виде мурашей. Это проблема экрана, а не
   качества обработки касаний, и ни одна библиотека от неё не спасает — спасает
   только фокус-навигация.

Побочный выигрыш: MIT/ISC вместо GPL, репозиторий может быть приватным.

Риски выбора приняты осознанно: версия 0.9.0, по сути один мейнтейнер, есть платная
premium-редакция. Митигация — изоляция (см. 5.2): про библиотеку знают ровно два
файла.

### 2.2 Модель родства: father_id / mother_id

Выбрана простая модель — две ссылки на родителей прямо на человеке, вместо
GEDCOM-подобной таблицы союзов. Покрывает подавляющее большинство реальных случаев,
даёт простые запросы, легко чинится.

**Но таблица `spouses` всё равно нужна.** family-chart требует список супругов для
отрисовки. Его можно вычислять из общих детей, и для предков это работает всегда (у
твоих родителей есть общий ребёнок — ты). Ломается на бездетных парах: жена брата,
у которой пока нет детей; бездетные тётя с дядей. Поэтому `spouses` существует, но
остаётся минимальной: **дети по-прежнему висят на `father_id`/`mother_id`, а не на
союзе.** Это не превращает модель в отвергнутые unions.

Братья и сёстры не хранятся — выводятся из общих родителей.

### 2.3 Поток данных: SvelteKit form actions

Мутации идут через form actions с серверным клиентом `@supabase/ssr`, а не прямыми
вызовами `supabase-js` из браузера. Сессия — в httpOnly-куках, маршруты охраняет
`hooks.server.ts`, RLS остаётся второй линией обороны, а не единственной. Формы
работают до гидрации JS.

### 2.4 Полный экран человека и смысл тапа

Тап имеет два возможных смысла — «перейти к человеку» и «раскрыть подробности».
Разведены так:

- **Тап по чужой карточке** — перецентрировать дерево на этом человеке.
- **Тап по карточке, которая уже в центре** — раскрыть полный экран.
- На карточке в фокусе счётчики `↑2 ♥1 ↓3` дополнительно работают кнопками-переходами.

Обоснование: самое частое действие (ходить по дереву) сохраняет самый большой
тап-таргет — всю карточку. И схема сама себя объясняет: первый тап видимо двигает
дерево, значит смысл тапа выучен; а у карточки в центре «перейти» уже не имеет
смысла, остаётся «раскрыть».

Долгий тап как жест не используется: на телефоне он недискаверабелен и воюет с
выделением текста и контекстным меню браузера.

### 2.5 Полный экран — настоящий маршрут через shallow routing

`/person/[id]` — реальный маршрут, а не компонент-оверлей. Причины по убыванию
важности:

1. **Кнопка «назад» на Android закрывает карточку, а не приложение.** Оверлей без
   интеграции с историей — классический баг PWA: жмёшь «назад» закрыть окно и
   вылетаешь из приложения.
2. Ссылку на человека можно скинуть родне.
3. Данные грузятся на сервере, без спиннера.

Открывается через **shallow routing** SvelteKit (`preloadData` + `pushState`): дерево
остаётся смонтированным под оверлеем, панель выезжает поверх, «назад» её закрывает.
Обычная навигация здесь не годится — диаграмма размонтировалась бы, d3 нарисовал всё
заново, зум и позиция потерялись бы.

Прямой заход по ссылке или работа без JS отрисуют тот же `/person/[id]`
самостоятельной страницей. Один `+page.server.ts` обслуживает оба случая.

### 2.6 Уведомления: два слоя

**Слой 1 — экран «Ближайшие события»** внутри приложения. Список: сегодня, на этой
неделе, в этом месяце. Ноль инфраструктуры, ноль разрешений, работает везде, включая
iOS без установки.

**Слой 2 — Web Push.** Ограничения, под которые спроектировано:

- **Vercel Hobby разрешает крон только раз в сутки**, и то с гарантией лишь в
  пределах указанного часа; более частое выражение падает на деплое. Поэтому
  «поздравить ровно в 9 утра по местному» невозможно. Обход: один прогон в 03:00 UTC,
  а уведомление говорит не «прямо сейчас», а «сегодня и в ближайшие `lead_days`
  дней». Точный час перестаёт быть важен, и таймзонная возня исчезает.
- **iOS: пуш работает только у установленной PWA** (iOS 16.4+, «Поделиться → На экран
  Домой»), разрешение запрашивается только по тапу пользователя, автоматического
  предложения установки нет. Нужен экран-инструкция с картинками.
- **Пуш иногда не долетает** — телефон спит, разрешение отозвано, endpoint протух.
  Поэтому пуш не единственный канал: слой 1 существует всегда.

**Дата смерти обязательна для этой фичи.** Без `died_on` приложение напишет «сегодня
день рождения дедушки» через два года после похорон, и напишет всей семье. Одно
nullable-поле снимает проблему.

Сценарий, который склеивает уведомления с контактами:
уведомление → тап → полный экран человека → кнопка WhatsApp → поздравил.

### 2.7 Язык в БД, а не только в куке

Крон рассылает пуши без запроса от пользователя: куки нет, `Accept-Language` нет.
Текст «Сегодня 78 лет Марии» надо на чём-то построить, поэтому локаль хранится в
`user_settings.locale`. Кука `locale` — лишь кэш для рендера страниц; переключатель
языка пишет в оба места.

### 2.8 i18n своими руками, не Paraglide

`@inlang/paraglide-js` 2.23.0 — идиоматичный для SvelteKit вариант, но на два языка и
~80 строк интерфейса он приносит vite-плагин, каталог `project.inlang` и шаг
компиляции. Свой словарь — около 40 строк, ноль зависимостей, ноль кодогенерации, а
типобезопасность та же: `en.ts` объявляется через `satisfies typeof ru`, и TypeScript
сам сообщает о забытом переводе. Paraglide берём, если языков станет больше двух.

Локаль читается в `hooks.server.ts` и подставляется в `<html lang="%lang%">` из
`app.html` — **нет вспышки не того языка** при загрузке.

Склонения и форматы — через `Intl`, не своими `if`: `Intl.DateTimeFormat` для дат,
`Intl.PluralRules` для «1 год / 2 года / 5 лет».

## 3. Схема базы данных

```sql
create table trees (
  id             uuid primary key default gen_random_uuid(),
  owner_id       uuid not null references auth.users(id) on delete cascade,
  name           text not null,              -- задаётся приложением на языке пользователя
  root_person_id uuid,                      -- с кого открывается вид
  created_at     timestamptz not null default now()
);

create table people (
  id         uuid primary key default gen_random_uuid(),
  tree_id    uuid not null references trees(id) on delete cascade,
  first_name text not null,
  last_name  text,
  gender     text not null check (gender in ('male','female')),
  birth_date date,          -- nullable: у предков её часто нет
  died_on    date,          -- nullable; not null => человек считается умершим
  email      text,
  phone      text,          -- E.164, например +79161234567
  telegram   text,          -- username без @
  instagram  text,          -- username без @
  about      text,
  father_id  uuid references people(id) on delete set null,
  mother_id  uuid references people(id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table spouses (
  tree_id     uuid not null references trees(id) on delete cascade,
  person_a_id uuid not null references people(id) on delete cascade,
  person_b_id uuid not null references people(id) on delete cascade,
  married_on  date,
  primary key (person_a_id, person_b_id),
  check (person_a_id < person_b_id)         -- пара хранится один раз
);

alter table trees add constraint trees_root_fk
  foreign key (root_person_id) references people(id) on delete set null;

create table user_settings (
  user_id      uuid primary key references auth.users(id) on delete cascade,
  locale       text not null default 'ru' check (locale in ('ru','en')),
  push_enabled boolean not null default false,
  lead_days    int not null default 3 check (lead_days between 0 and 30)
);

create table push_subscriptions (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid not null references auth.users(id) on delete cascade,
  endpoint   text not null unique,
  p256dh     text not null,
  auth       text not null,
  created_at timestamptz not null default now()
);

create table notifications_sent (
  user_id     uuid not null references auth.users(id) on delete cascade,
  kind        text not null check (kind in ('birthday','anniversary')),
  subject_key text not null,     -- id человека либо 'a_id:b_id' для пары
  event_date  date not null,
  sent_at     timestamptz not null default now(),
  primary key (user_id, kind, subject_key, event_date)
);

create index people_tree_idx    on people(tree_id);
create index people_father_idx  on people(father_id);
create index people_mother_idx  on people(mother_id);
create index spouses_tree_idx   on spouses(tree_id);
create index push_user_idx      on push_subscriptions(user_id);
```

`subject_key` вместо `person_id`, потому что годовщина принадлежит паре, а не
человеку. Таблица защищает от задвоения при повторном прогоне крона.

Поиск дней рождения в окне дат в SQL требовал бы индексов по (месяц, день) и
аккуратной обработки перехода через год. Данных мало (дерево на 200 человек — это
~50 КБ JSON), поэтому люди и браки дерева выгружаются целиком, а окно считает чистая
функция `upcoming.ts`.

### 3.1 RLS

```sql
alter table trees              enable row level security;
alter table people             enable row level security;
alter table spouses            enable row level security;
alter table user_settings      enable row level security;
alter table push_subscriptions enable row level security;
alter table notifications_sent enable row level security;

create policy trees_owner on trees for all
  using (owner_id = auth.uid()) with check (owner_id = auth.uid());

create policy people_owner on people for all
  using      (exists (select 1 from trees t where t.id = people.tree_id and t.owner_id = auth.uid()))
  with check (exists (select 1 from trees t where t.id = people.tree_id and t.owner_id = auth.uid()));

create policy spouses_owner on spouses for all
  using      (exists (select 1 from trees t where t.id = spouses.tree_id and t.owner_id = auth.uid()))
  with check (exists (select 1 from trees t where t.id = spouses.tree_id and t.owner_id = auth.uid()));

create policy settings_own on user_settings for all
  using (user_id = auth.uid()) with check (user_id = auth.uid());

create policy subs_own on push_subscriptions for all
  using (user_id = auth.uid()) with check (user_id = auth.uid());
```

Для `notifications_sent` политик нет — таблица доступна только серверу под секретным
ключом, который RLS обходит.

Все политики объявляются с `to authenticated` и с `(select auth.uid())` в подзапросе:
без `TO` политика проверяется и для `anon`, а голый `auth.uid()` пересчитывается на
каждую строку. `for all` покрывает и `using`, и `with check` — без `with check`
пользователь смог бы переписать `owner_id` на чужой.

**Экспозиция в Data API.** С 28 апреля 2026 новые таблицы в схеме `public` больше не
попадают в Supabase Data API автоматически. Значит после миграции нужен явный
`grant` для роли `authenticated` и проверка запросом — иначе PostgREST будет отдавать
пустоту без внятной ошибки.

В дереве хранятся телефоны и инстаграмы живой родни — персональные данные третьих
лиц. Следствия обязательные, не рекомендательные: политики RLS покрыты тестом (§8),
`SUPABASE_SERVICE_ROLE_KEY` не появляется в клиентском бандле ни при каких условиях,
публичного шаринга дерева нет.

### 3.2 Инварианты

Postgres не выражает их через `check` (нужны обращения к другим строкам), поэтому они
проверяются на сервере в `lib/server/people.ts` перед записью:

1. `father_id` указывает на человека с `gender = 'male'`, `mother_id` — на `'female'`.
2. Родитель принадлежит тому же дереву; `father_id != id`, `mother_id != id`.
3. **Нет циклов** — человек не может быть своим предком. Не педантизм: цикл уведёт
   раскладку family-chart в бесконечную рекурсию и повесит телефон. Проверяется
   рекурсивным обходом предков перед сохранением.
4. Оба супруга в `spouses` принадлежат тому же дереву.
5. `died_on >= birth_date`, если оба заполнены.

### 3.3 Удаление человека

У детей `father_id`/`mother_id` становятся `null` (`on delete set null`), строки
супружества исчезают (`on delete cascade`), `trees.root_person_id` обнуляется, если
удалён корень. В диалоге подтверждения перечисляются те, кто останется без родителя.

## 4. Интерфейс

### 4.1 Экраны

| Маршрут | Содержимое |
|---|---|
| `/login`, `/signup` | Email и пароль |
| `/` (пустое дерево) | «Расскажите о себе» → первый человек становится корнем |
| `/` | Диаграмма во весь вьюпорт, компактный хедер |
| `/person/[id]` | Полный экран человека; поверх дерева через shallow routing |
| `/events` | Ближайшие события: сегодня, на этой неделе, в этом месяце |
| `/settings` | Язык, уведомления, подписка на пуш, инструкция для iOS |

### 4.2 Карточка в дереве

```
┌──────────────────────────────────┐
│  ╭────╮   Мария                  │
│  │ МП │   Петрова                │
│  ╰────╯   1948 — 78 лет          │
│  ──────────────────────────────  │
│   ↑ 2    ♥ 1    ↓ 3         ⓘ   │
└──────────────────────────────────┘
```

Роль каждого элемента:

- **Круг с инициалами** вместо пустого места под фото. Цвет — приглушённый акцент по
  полу (тёплый песочный / прохладный сине-зелёный), не «розовый-голубой».
- **Имя крупно, фамилия тоньше** — типографская иерархия вместо одной серой строки.
- **Годы, не полная дата.** `1948 — 78 лет` у живых, `1948–2011` у умерших. Точная
  дата живёт в форме; на карточке она только шумит.
- **Счётчики `↑2 ♥1 ↓3`** — родители, супруги, дети. Главная польза карточки: в
  фокус-навигации иначе не видно, есть ли за ней неисследованная ветка. `↓3`, когда
  на экране один ребёнок, прямо говорит «тапни, там ещё двое».
- **Точка-индикатор незаполненности** — нет даты рождения или пустой About.
  Превращает дерево в чек-лист: видно, что достроить.
- **`ⓘ`** появляется только если About непустой.
- Карточка в фокусе крупнее и с тенью, остальные приглушены.
- Вся карточка — тап-таргет не меньше 44px. Длинные имена обрезаются по ellipsis,
  раскладка не прыгает.

### 4.3 Полный экран человека

Крупный круг с инициалами, имя и фамилия; дата рождения в локальном формате и
возраст; About целиком со скроллом; ряд крупных кнопок-контактов (`tel:`, `wa.me`,
`t.me`, `instagram.com`, `mailto:`) — **только заполненные, пустых серых заглушек
нет**; список родственников с переходами: родители, супруги, дети, братья и сёстры.

Действия: «Изменить», «Добавить родственника», «Удалить», «Показать в дереве»
(перецентрирует и закрывает).

Режим правки — на том же экране: «Изменить» превращает поля в инпуты, одна форма,
один `?/update`. Отдельный маршрут `/edit` был бы лишним тапом на телефоне.

### 4.4 Стили

Токены (цвета, радиусы, тени, шрифтовая шкала, отступы) — CSS custom properties в
`src/lib/styles/tokens.css`. Тёмная тема через `prefers-color-scheme` — вечером на
телефоне это не украшение.

**Карточки требуют глобальных стилей.** Их вставляет в DOM сам d3, вне Svelte-дерева,
поэтому scoped-стили Svelte до них не долетят. Поэтому: карточки — в глобальном
`cards.css`, всё остальное — обычные scoped `<style>` в компонентах. Токены общие, так
что цвета и тёмная тема остаются в одном месте.

HTML карточек генерит `lib/tree/card.ts`, ей передаётся `t` — «78 лет» переводится
вместе со всем остальным.

### 5.1 Границы модулей

`lib/tree/to-family-chart.ts`, `lib/events/upcoming.ts` и `lib/i18n/*` — чистые
функции без доступа к сети и БД. Каждую можно понять и протестировать в одиночку.

`lib/server/people.ts` владеет всеми инвариантами из 3.2. Ни один роут не пишет в
`people` напрямую.

### 5.2 Изоляция family-chart

`FamilyTree.svelte` — **единственный** файл, знающий про API библиотеки; `card.ts` —
единственный, знающий про формат её карточек. Если библиотека подведёт (0.9.0, один
мейнтейнер), менять придётся эти два файла, а не всё приложение. Путь отхода —
`@xyflow/svelte` + собственная раскладка.

### 5.3 Формат данных family-chart

Библиотека 0.9.0+ ждёт `rels.parents: [id, id]` (массив вместо отдельных `father` и
`mother`), пол как `"M"`/`"F"`, и **связи должны быть двусторонними**: если A указал
B супругом, B обязан указать A, и массивы `children` тоже должны быть заполнены.

Наша БД нормализована, поэтому `to-family-chart.ts` разворачивает её в этот
избыточный граф: выводит `children` из `father_id`/`mother_id`, зеркалит супругов,
маппит `male|female` → `M|F`. Чистая функция, покрыта тестами.

### 5.4 Поток данных и перерисовка

`(app)/+page.server.ts` делает два запроса (люди дерева, браки дерева), вызывает
`toFamilyChart()` на сервере и отдаёт клиенту готовый граф.

`FamilyTree.svelte` монтирует f3 в `onMount` и держит до `onDestroy`. После правки
делается `invalidateAll()`, новые данные приезжают, и `$effect` обновляет store
библиотеки, **не пересоздавая её** — иначе слетят зум и фокус, и каждая правка будет
ощущаться как перезагрузка страницы.

### 5.5 Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Нарушен инвариант (пол родителя, цикл, чужое дерево) | `fail(400, {field, message})`, ошибка у конкретного поля |
| Сессия протухла | Редирект `/login?redirectTo=…`, после входа возврат туда, где был |
| Нет сети | SW отдаёт кэш, баннер, кнопки правки disabled |
| Supabase недоступен | `error(503)` и человеческий экран, а не белый |
| Пуш вернул `410`/`404` | Подписка удаляется |
| Крон без `CRON_SECRET` | `401` |

## 6. PWA

Свой `service-worker.ts` через `$service-worker` (SvelteKit отдаёт `build`, `files`,
`version`) — около 40 строк и полный контроль, без ещё одного плагина в сборке.

- Precache app shell (`build` + `files`), версия кэша из `version`.
- Навигация: network-first с фоллбэком на кэш.
- `/api/*`: только сеть, без кэша.
- Обработчики `push` и `notificationclick` в том же файле; тап по уведомлению
  открывает `/person/<id>`.

Манифест: `standalone`, иконки 192/512 и maskable-512, `theme_color` из токенов.

Офлайн-баннер в `+layout.svelte` по `navigator.onLine` и событиям `online`/`offline`;
кнопки правки в офлайне disabled.

## 7. Уведомления — реализация

`/api/cron/events` (GET, `Authorization: Bearer $CRON_SECRET`), Vercel Cron
`0 3 * * *`. Работает под `service_role`, чтобы обойти RLS и разослать всем.

Алгоритм:

1. Взять пользователей с `push_enabled = true` и их `locale`, `lead_days`.
2. Для каждого выгрузить людей и браки его дерева.
3. `upcoming.ts` считает события в окне `[сегодня, сегодня + lead_days]`. Умершие
   (`died_on is not null`) в дни рождения не попадают. Годовщины — только у браков с
   заполненным `married_on`, и только если оба супруга живы.
4. Отбросить то, что уже есть в `notifications_sent`.
5. Отправить `web-push` на все подписки пользователя, текст на его `locale`.
6. `410`/`404` → удалить подписку. Успех → записать в `notifications_sent`.

`/settings` подписывает на пуш: запрос разрешения строго по тапу (требование iOS),
`POST /api/push/subscribe` с endpoint и ключами. Для iOS — блок-инструкция
«Поделиться → На экран Домой» с указанием, что без установки пуши не работают.

## 8. Тестирование

Vitest на чистые функции:

- `to-family-chart`: двусторонние связи; `children` выведены из `father_id`/`mother_id`;
  супруги зеркальны; одинокий человек без связей; маппинг пола.
- Детектор циклов: прямой (сам себе отец) и длинный (A → B → C → A).
- `upcoming.ts`: **переход через год** — ДР 3 января при прогоне 31 декабря должен
  попасть в окно. Это тот баг, который в проде всплывает ровно один раз в году.
- `upcoming.ts`: `died_on is not null` не даёт события дня рождения; годовщина без
  `married_on` не создаётся.
- i18n: все ключи `ru` есть в `en`; возраст через `Intl.PluralRules`
  («1 год / 2 года / 5 лет»).

Тест RLS: под пользователем B не видно людей дерева A. Там телефоны родни, это не
формальность.

Playwright, один сквозной путь: регистрация → добавил себя → добавил отца → правка →
виден в дереве → появился в «Ближайших событиях».

Не тестируем: раскладку d3, реальную доставку пушей.

## 9. Деплой

`@sveltejs/adapter-vercel`. Миграции — `supabase/migrations/*.sql` через Supabase CLI.
Крон объявляется в конфиге проекта Vercel: `0 3 * * *` на `/api/cron/events`.

Переменные окружения:

| Переменная | Где нужна |
|---|---|
| `PUBLIC_SUPABASE_URL` | клиент и сервер |
| `PUBLIC_SUPABASE_PUBLISHABLE_KEY` | клиент и сервер (publishable, не legacy `anon`) |
| `SUPABASE_SECRET_KEY` | только крон; в клиентский бандл не попадает |
| `VAPID_PUBLIC_KEY` | клиент (подписка) и сервер |
| `VAPID_PRIVATE_KEY` | только сервер |
| `VAPID_SUBJECT` | только сервер (`mailto:…`) |
| `CRON_SECRET` | только сервер |

## 10. Принятые риски

- **family-chart 0.9.0**, один мейнтейнер, есть платная premium-редакция. Митигация —
  изоляция в двух файлах (5.2).
- **Пол только `male`/`female`** — от него зависят и роли отец/мать, и раскладка
  библиотеки. Небинарного варианта в этой модели не будет.
- **Один родитель одного пола** — модель не выражает двух отцов или двух матерей.
- **Неточных дат нет.** `birth_date` либо точная, либо пустая; «около 1920» ввести
  некуда. На дальних предках это будет ощущаться.
- **Крон раз в сутки** (ограничение Vercel Hobby) — уведомление приходит в окне
  «сегодня и ближайшие N дней», а не в конкретный час по местному времени.
- **iOS-пуши только у установленной PWA.** Пользователь, открывший приложение в
  браузере, уведомлений не получит — увидит только экран «Ближайшие события».
